# SFTP Backup Vault

**صندوق بکاپی که فقط فایل می‌پذیرد.** سرورهای شما بکاپ‌هایشان را با همان SFTP معمولی می‌فرستند، ولی حساب‌های بکاپ فقط می‌توانند *آپلود* کنند. هر آپلودی که کامل شد، ظرف چند دقیقه به انباری منتقل می‌شود که آن حساب حتی آن را نمی‌بیند. آنجا فایل مال root است، فقط‌خواندنی و تغییرناپذیر، و SHA-256اش ثبت شده است. بکاپ‌های قدیمی هم به‌روش پدربزرگ-پدر-پسر چرخیده می‌شوند.

پس اگر یکی از سرورهایتان هک شود، هکر رمز یا کلید بکاپ آن سرور را دارد و باز هم نمی‌تواند حتی یکی از بکاپ‌هایی را که پیش‌تر فرستاده شده پاک کند، عوض کند، رمزگذاری کند یا دانلود کند.

## چرا

روش رایج نگه داشتن بکاپ بیرون از سرور این است که سرور بکاپ‌هایش را با SFTP روی ماشین دیگری آپلود کند، با رمز یا کلیدی که روی خود سرور است. نقطهٔ ضعف همین رمز است: هر کس سرور را بگیرد، با همان رمز وارد سرور بکاپ می‌شود و همهٔ بکاپ‌ها را پاک می‌کند، عوض می‌کند یا می‌دزدد. باج‌افزارها هم دقیقاً همین کار را می‌کنند، پیش از آنکه چیزی را رمزگذاری کنند.

SFTP Backup Vault همان روش ساده‌ای را نگه می‌دارد که همهٔ پنل‌های هاستینگ، افزونه‌ها و اسکریپت‌ها بلدند («فایل را با SFTP بفرست») و خطرش را در سمت گیرنده از بین می‌برد.

## چطور کار می‌کند

```
 سرور شما ──SFTP──► /var/backups/sftp/<حساب>/upload     تنها پوشه‌ای که حساب می‌بیند (chroot)
                                │  هر دقیقه: آپلودی که بسته شده و ۲ دقیقه دست نخورده
                                ▼
                       /var/backups/vault/<حساب>/          فقط root · 0400 · chattr +i · SHA-256 ثبت‌شده
                                │  هر شب: چرخش پدربزرگ-پدر-پسر
                                ▼
                       /var/backups/vault/.trash/<تاریخ>/   ۷ روز می‌ماند، بعد پاک می‌شود
```

| حساب بکاپ می‌تواند | نمی‌تواند |
|---|---|
| با SFTP وارد شود (رمز یا کلید) | شل بگیرد، فرمان اجرا کند یا پورت را forward کند |
| زیر `upload/` پوشه بسازد و فایل آپلود کند | هیچ فایلی را بخواند (دانلود کند) |
| `upload/` و آپلودهای در جریانِ خودش را ببیند | فایل یا پوشه‌ای را پاک کند |
| نام یا دسترسی یک آپلودِ در جریان را عوض کند (بعضی برنامه‌ها با نام موقت آپلود می‌کنند) | پیوند یا کپی روی سرور بسازد |
| | انبار یا هر چیزی بیرون از chroot خودش را ببیند |
| | جز از سرور خودش وارد شود (اختیاری و توصیه‌شده) |

- **قواعد را خود sshd اجرا می‌کند.**
- **بررسی سالم رسیدن:** zip، gzip و tar هنگام رسیدن بررسی می‌شوند تا معلوم شود ناقص نرسیده‌اند. پوشهٔ بکاپی که `SHA256SUMS` یا `manifest.json` خودش را دارد، با آن سنجیده می‌شود.
- **بررسی دوباره:** هر هفته همهٔ فایل‌های انبار دوباره هش می‌شوند.
- **گزارش:** هر کار حساب‌ها و هر درخواستِ ردشده در `/var/log/auth.log` ثبت می‌شود و وضعیت بکاپ‌ها هنگام ورود به سرور نشان داده می‌شود.

## پیش‌نیازها

- لینوکس با systemd. در CI روی **Ubuntu 22.04 و 24.04** آزموده می‌شود و روی Debian 11 به بعد هم باید کار کند.
- OpenSSH 7.8 یا تازه‌تر، با `Include /etc/ssh/sshd_config.d/*.conf` در `sshd_config`.
- پایتون 3.8 یا تازه‌تر و e2fsprogs. rsyslog برای ثبت کارهای حساب‌ها لازم است.
- فایل‌سیستمی که نشان تغییرناپذیری (immutable) را پشتیبانی کند (ext4، XFS، Btrfs).

نصب‌کننده هر بسته‌ای را که کم باشد پیشنهاد نصب می‌دهد.

## نصب

روی سرور بکاپ:

```bash
curl -fsSL https://raw.githubusercontent.com/MahdiGraph/SFTP-Backup-Vault/main/install.sh | sudo bash
```

یا، برای اینکه اول اسکریپت را بخوانید:

```bash
git clone https://github.com/MahdiGraph/SFTP-Backup-Vault.git
cd SFTP-Backup-Vault
sudo ./install.sh
```

نصب‌کننده:
- تنظیمات فعلی SSH را در `/var/lib/backup-vault/install-<زمان>/` نگه می‌دارد.
- فقط یک بلوک `Match Group sftp_backups` اضافه می‌کند و به حساب‌های دیگر دست نمی‌زند.
- نتیجه را با `sshd -t` می‌سنجد و مطمئن می‌شود شما را بیرون نمی‌اندازد، بعد sshd را بی قطع شدن نشست‌ها از نو بارگذاری می‌کند.
- در پایان `selftest` را اجرا می‌کند: با یک حساب موقت هر کاری را که یک هکر ممکن است بکند امتحان می‌کند.

`--keys-only` ورود حساب‌های بکاپ را فقط با کلید می‌گذارد. بی آن، رمز هم پذیرفته می‌شود، چون خیلی از برنامه‌های بکاپ چیزی جز رمز ندارند.

## شروع سریع

برای هر سروری که بکاپ می‌فرستد یک حساب بسازید. `--from` آن را به نشانی همان سرور محدود می‌کند:

```bash
sudo backup-vault add-user site1 --from 203.0.113.10 --password
```

در برنامهٔ بکاپ آن سرور بنویسید:
- پروتکل: SFTP
- نشانی و پورت: سرور بکاپ و پورت SSH آن
- کاربر: `site1`
- پوشه: `upload`

بعد از اولین بکاپ:

```bash
sudo backup-vault status          # وضعیت همهٔ حساب‌ها
sudo backup-vault list site1      # بکاپ‌های یک حساب، تازه‌ترین بالا
```

اگر هر بکاپ یک پوشه با چند فایل است (مثلاً دیتابیس، فایل‌ها و فهرست هش)، `--set-by folder` بگذارید تا چرخش آن پوشه را یک بکاپ بشمارد.

## برنامه‌های بکاپ

هر چیزی که فقط فایل آپلود کند کار می‌کند:
- `sftp`، `scp` (OpenSSH 9 به بعد)، `lftp` و rclone؛
- Flysystem در PHP، و در نتیجه بکاپ‌های لاراول؛
- اسکریپت‌های cron؛
- پنل‌ها و افزونه‌هایی که «بکاپ را به سرور SFTP بفرست» دارند.

چند نکته:
- **پاک کردن بکاپ‌های قدیمی از سمت برنامه رد می‌شود.** چرخش را به انبار بسپارید.
- **برنامه‌ای که فایل آپلودشده را برای وارسی دوباره می‌خواند، در همان مرحله شکست می‌خورد.**
- **restic، Borg، Kopia، Duplicity و rsync** که مخزن راه‌دورشان را می‌خوانند یا فرمان اجرا می‌کنند، عمداً کار نمی‌کنند.
- **بکاپ را در سمت فرستنده رمزگذاری کنید.** انبار جلوی پاک شدن و عوض شدن را می‌گیرد؛ کسی که روی خود سرور بکاپ root باشد، هنوز می‌تواند بخواند.

## چرخش

هر شب ساعت ۰۵:۱۵، از بکاپ‌های هر حساب این‌ها می‌مانند:

| تنظیم | پیش‌فرض | نگه می‌دارد |
|---|---|---|
| `keep_all_days` | ۷ | همهٔ بکاپ‌های ۷ روز اخیر |
| `daily` | ۳۰ | تازه‌ترینِ هر روز، تا ۳۰ روز |
| `weekly` | ۱۲ | تازه‌ترینِ هر هفته، تا ۱۲ هفته |
| `monthly` | ۱۲ | تازه‌ترینِ هر ماه، تا ۱۲ ماه |
| `yearly` | ۳ | تازه‌ترینِ هر سال، تا ۳ سال |
| `keep_last` | ۷ | همیشه ۷ بکاپِ آخر، هر قدر قدیمی (دست‌کم ۱) |
| `trash_days` | ۷ | چند روز بکاپِ کنارگذاشته در سطل زباله بماند |

این پنجره‌ها از امروز به عقب شمرده می‌شوند. پس سیل آپلودهای بی‌ارزش، بکاپ‌های قدیمی را زودتر از موعد بیرون نمی‌راند.

پشتیبان‌هایی که نامشان فقط در عدد فرق دارد یک «سری»اند و هر سری جدا چرخیده می‌شود.

چرخش هیچ‌وقت برای جا باز کردن چیزی پاک نمی‌کند، تا پر کردن دیسک راهی برای از بین بردن بکاپ‌ها نباشد. وقتی هم ساعت سرور هم‌زمان نیست، کاری نمی‌کند.

تنظیمات در `/etc/backup-vault/backup-vault.conf` است و هر حساب می‌تواند تنظیمات خودش را داشته باشد. برای مثال، برای اینکه `site1` ۶۰ روز بکاپ روزانه نگه دارد:

```ini
[account site1]
daily = 60
```

پیش از اینکه به تغییری تکیه کنید، اثرش را ببینید:

```bash
sudo backup-vault policy               # تنظیماتی که هر حساب با آن کار می‌کند
sudo backup-vault rotate --dry-run     # چرخش امشب چه چیزی را به سطل زباله می‌برد
```

## فرمان‌ها

| فرمان | کار |
|---|---|
| `status` | وضعیت همهٔ حساب‌ها و هشدارها |
| `list NAME` | بکاپ‌های یک حساب و دلیل نگه داشتن هر کدام |
| `policy` | تنظیماتی که هر حساب با آن کار می‌کند |
| `add-user NAME --from IP --password` | ساخت حساب بکاپ (یا `--key "ssh-ed25519 ..."`) |
| `set-ip NAME IP` | نشانی‌ای که حساب از آن وارد می‌شود (`none` برای برداشتن) |
| `set-key NAME "ssh-ed25519 ..."` | کلید SSH حساب |
| `disable-user` / `enable-user NAME` | بستن یا باز کردن ورود حساب؛ بکاپ‌هایش می‌مانند |
| `remove-user NAME` | حذف حساب؛ بکاپ‌هایش می‌مانند |
| `copy-out NAME BACKUP FOLDER` | کپی یک بکاپ از انبار برای بازگردانی |
| `rotate --dry-run` | دیدن کار چرخش بی انجام دادن آن |
| `verify` | هش دوبارهٔ همهٔ فایل‌های انبار |
| `selftest` | آزمودن حق‌های یک حساب موقت روی sshd واقعی |

همهٔ فرمان‌ها با `sudo backup-vault` اجرا می‌شوند.

## بازگردانی

```bash
sudo backup-vault list site1
mkdir -p ~/restore
sudo backup-vault copy-out site1 site1-2026-11-01 ~/restore
```

کپی مال خود شماست. فایل‌های داخل انبار را دستی پاک یا جابه‌جا نکنید؛ این کار با چرخش است.

## نکته‌های امنیتی

**در برابر چه چیزی محافظت می‌کند:** بکاپ‌هایی که پیش از هک یک سرور رسیده‌اند. با حساب بکاپ آن سرور نه پاک می‌شوند، نه عوض می‌شوند و نه خوانده می‌شوند.

**در برابر چه چیزهایی محافظت نمی‌کند:**
- root روی خود سرور بکاپ. آن ماشین را جدا و حداقلی نگه دارید و فقط با کلید واردش شوید.
- بکاپ‌هایی که پس از هک فرستاده می‌شوند.
- پر شدن دیسک. بکاپ‌های تازه شکست می‌خورند، ولی هیچ‌کدام از بکاپ‌های موجود از دست نمی‌رود.

**توصیه‌ها:**
- **هر حساب را به سرور خودش ببندید** (`--from` یا `set-ip`). این کار ورود هر حساب دیگری را هم از آن نشانی‌ها می‌بندد، پس کسی که آنجاست حتی نمی‌تواند رمز مدیر را امتحان کند.
- **کلید را به رمز ترجیح دهید.**
- **با دیوار آتش، SSH را فقط برای سرورهای خودتان باز کنید.**
- **بکاپ‌ها را رمزگذاری‌شده بفرستید.**

## به‌روزرسانی و حذف

- **به‌روزرسانی:** نصب‌کننده را دوباره اجرا کنید. تنظیمات، حساب‌ها، کلیدها و بکاپ‌ها می‌مانند.
- **حذف:** `sudo ./uninstall.sh`. برنامه و قواعدش را برمی‌دارد، ولی هرگز بکاپ‌ها را پاک نمی‌کند. حساب‌های بکاپ را هم قفل می‌کند، چون بی آن قواعد کاربر معمولی سرور می‌شوند.
